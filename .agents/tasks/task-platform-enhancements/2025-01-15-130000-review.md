# Platform enhancements: Plugin SDK, SignalR streaming, audit trail, Storage Replica, session management (v2)

The fix commit addresses the most critical findings from v1: `PluginSandboxService` is now registered in DI, `StorageReplicaController` validates all user-supplied inputs against strict regex patterns before interpolation, `ServerContextProvider` wraps the component tree in `__root.tsx`, and SignalR lifecycle handlers use a `mountedRef` guard to prevent stale state updates. The audit hash-chain concurrency and purge-boundary limitations are now documented inline as known trade-offs.

Watch for: `SharePointSetupController` still interpolates user-supplied paths, URLs, and server names into PowerShell scripts without any sanitization (confirmed) — the same class of injection the StorageReplica fix addressed. No route page consumes `useServerContext()` (confirmed), so the provider is mounted but functionally inert — the multi-server context goal remains unmet. The `GetPartnerships` endpoint still returns `Ok(empty)` on failure (confirmed), preventing the frontend from distinguishing "no data" from "server error."

**Verdict**: NEEDS_CHANGES

## High-level view

The StorageReplicaController injection fix is well-scoped: regex allowlists reject malicious characters before they reach string interpolation. However, `SharePointSetupController` performs exactly the same pattern — `'{p.FileSharePath}'`, `'{conf.SqlDownloadUrl}'`, `'{conf.SqlTargetServer}'` — and received no corresponding validation. This is the remaining blocking security concern.

The `ServerContextProvider` is now mounted around the component tree, but no page imports or calls `useServerContext()`. Every page still manages its own local `server` state via `useState`. The provider won't affect behavior until pages are migrated to consume it, so the multi-server context feature remains structurally incomplete.

The SignalR `mountedRef` guard prevents stale state updates, but each mount of `useSignalR` still registers new `onreconnecting`/`onreconnected`/`onclose` callbacks that can never be removed from the `HubConnection` instance. The callback array grows linearly with mount/unmount cycles over the session lifetime.

## SharePointSetupController still has unmitigated injection surface

The `ExecuteSetup` action interpolates user-controlled fields into PowerShell scripts without any validation or escaping:

```csharp
dcScript.AppendLine($@"
$path = '{p.FileSharePath}'
...
New-SmbShare -Name $shareName -Path $path -FullAccess 'Everyone'
");
```

And later:

```csharp
var sqlScript = $@"
$share = '{p.FileShareUrl}'
...
Start-Process -FilePath $setup -ArgumentList '/Q ... /INSTANCENAME=""{conf.SqlInstanceName}"" /INSTANCEDIR=""{conf.SqlDisk}:\"" /SQLSYSADMINACCOUNTS={sqlAdmins}' -Wait
";
```

A `FileSharePath` value like `'; Remove-Item C:\\ -Recurse -Force ; '` escapes the quoted context. The `SqlInstanceName`, `SqlDisk`, and `SqlAdmins` fields are similarly unvalidated. The fix is the same pattern already applied to `StorageReplicaController`: add regex validation methods and reject requests containing characters outside the allowlist before building the script string.

## ServerContextProvider mounted but never consumed

Grepping the codebase for `useServerContext` returns zero results in any route file. The pages that would benefit — `performance.tsx`, `storage-replica.tsx`, the VM pages — each declare local `useState("")` for server selection and pass it to their own `ServerSelector` component. The server choice is not shared across page navigations: navigating from performance (with server `dc01` selected) to storage-replica resets to an empty string.

The provider is correctly placed for future consumption, but the stated goal of "fix route pages to properly use the selected server context" requires the pages to import and use the hook.

## GetPartnerships error masking

```csharp
catch (Exception ex)
{
    _logger.LogError(ex, "Error fetching Storage Replica partnerships for server {ServerId}", serverId);
    return Ok(Array.Empty<ReplicaPartnershipDto>());
}
```

When the backend fails (connection timeout, PowerShell error, auth failure to the target server), the UI shows "No partnerships found" rather than an error. The same empty-on-error pattern appears in the happy path when `ExitCode != 0`. Returning a 500 (as the other endpoints in this controller already do for failures) would let the frontend's existing `toast.error()` handler fire.
