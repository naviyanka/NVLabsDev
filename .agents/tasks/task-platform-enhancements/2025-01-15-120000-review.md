# Platform enhancements: Plugin SDK, SignalR streaming, audit trail, Storage Replica, session management

Five features land in a single diff across 31 files: a plugin SDK with capability-based sandboxing, SignalR real-time metric streaming on the performance page, a full audit logging pipeline with hash-chain tamper detection, a Storage Replica controller wrapping PowerShell SR cmdlets, and PowerShell session management with configurable limits. The frontend builds cleanly. The backend targets `net8.0-windows` and cannot be compiled in this sandbox, so backend analysis is code-review only.

Watch for: `PluginSandboxService` is injected by `PluginsController` but **never registered in DI** (confirmed) — the app will throw at startup. The `StorageReplicaController` constructs PowerShell scripts via string interpolation of user input without sanitization (confirmed), creating a **command injection** surface. The `ServerContextProvider` is defined but never mounted or consumed by any route page (confirmed), so the multi-server context fix is incomplete. The audit middleware performs a database query (fetch last hash) on every authenticated request (confirmed), which becomes a serial bottleneck under load.

## High-level view

The plugin SDK introduces a `PluginManifest` model, a `PluginSandboxService` that validates PowerShell scripts against declared capabilities, and new controller endpoints for manifest retrieval and validation. The sandbox enforces a regex-based deny list scoped by capability enum, which is a reasonable first pass but has a DI registration gap that will crash the app.

SignalR integration replaces REST polling on the performance page with a persistent hub connection. A new `PerformanceStreamService` background service pushes telemetry every 2 seconds to server-specific groups. The frontend hook manages connection lifecycle and falls back to polling when disconnected. The singleton connection pattern is sound but lacks explicit teardown on app-level unmount.

The audit system is the most substantial addition: middleware captures every authenticated API request, computes a SHA-256 hash chain linking each entry to its predecessor, persists to a dedicated `NexusLogContext`, and exposes query/integrity/purge endpoints. A background `AuditRetentionService` runs daily purges. The hash-chain design provides tamper evidence, though the sequential last-hash lookup is a throughput concern and the purge operation silently breaks the chain.

Storage Replica gets a dedicated controller with 8 endpoints wrapping Windows SR cmdlets. It builds PowerShell scripts by interpolating route parameters and request body fields directly into script strings, which is the most serious security issue in this diff.

Session management gains configurable max sessions, idle timeout, and cleanup interval from `IConfiguration`, plus monitoring and force-cleanup endpoints. The `ServerContextProvider` React context was created but not integrated into the component tree or consumed by route pages.

1. **PluginSandboxService missing DI registration** — `PluginsController` constructor-injects `PluginSandboxService` but `Program.cs` never registers it. Add `builder.Services.AddTransient<PluginSandboxService>();` or equivalent.

4. **Audit hash-chain serial query on every request** — The middleware fetches the last entry's hash via `OrderByDescending(Timestamp).FirstOrDefault()` inside the request pipeline. Under concurrent requests this serializes writes and risks hash collisions or duplicates.
5. **Audit purge breaks hash chain** — Deleting old entries removes the `PreviousHash` anchor for the first remaining entry. Subsequent integrity verification will report a broken chain at the boundary.
6. **SharePointSetupController string interpolation injection** — Same pattern as StorageReplicaController: user-supplied paths, server names, and URLs are injected into PowerShell script text without sanitization.
7. **Audit middleware skips unauthenticated mutating requests** — Only authenticated requests are logged. Unauthenticated `POST`/`PUT`/`DELETE` that reach API endpoints (e.g., if auth is misconfigured or an endpoint is accidentally `[AllowAnonymous]`) will leave no audit trail.

## PluginSandboxService DI gap

`PluginsController` declares `PluginSandboxService` in its constructor, but `Program.cs` (the composition root) does not register it. The existing registrations end at `AddScoped<AuditLogService>()`:

```csharp
builder.Services.AddScoped<AuditLogService>();
builder.Services.AddHostedService<TelemetryBackgroundService>();
// No PluginSandboxService registration
```

ASP.NET Core will throw an `InvalidOperationException` at the first request to any `PluginsController` endpoint (or at startup if the container validates eagerly). This blocks the entire plugin feature.

## PowerShell command injection via string interpolation

`StorageReplicaController` constructs PowerShell commands like:

```csharp
var script = $@"
Remove-SRPartnership -Name '{partnershipId}' -Force -ErrorAction Stop
Remove-SRGroup -Name '{partnershipId}' -Force -ErrorAction SilentlyContinue
";
```

The `partnershipId` comes from the URL route segment — an authenticated user controls it. A value like `'; Invoke-Expression (malicious) ; '` escapes the quoted context and executes arbitrary commands. The same pattern appears in `CreatePartnership` (interpolating `request.SourceServer`, `request.DestServer`, `request.ReplicationGroup`, volume paths) and in `SharePointSetupController` (interpolating file paths, URLs, server names).

Mitigation: validate inputs against a strict allowlist pattern (e.g., `^[a-zA-Z0-9._-]+$` for server/partnership names), or pass values as PowerShell parameters via `-ArgumentList` rather than string interpolation.

## ServerContextProvider is dead code

`src/lib/serverContext.ts` exports `ServerContextProvider` and `useServerContext`, but:

- No component in the app wraps children with `<ServerContextProvider>`.
- No route page imports or calls `useServerContext()`.
- The `storage-replica.tsx` and `performance.tsx` pages manage their own local `server` state via `useState` and the existing `ServerSelector` component.

The stated goal of FEAT-003 ("fix route pages to properly use the selected server context") is unmet. The context exists as plumbing but is never wired in.

## Audit hash-chain throughput and correctness

The middleware computes the chain hash by fetching the most recent entry:

```csharp
var lastEntry = await logDb.AuditLogEntries
    .OrderByDescending(e => e.Timestamp)
    .Select(e => new { e.Hash })
    .FirstOrDefaultAsync();

entry.PreviousHash = lastEntry?.Hash;
entry.Hash = ComputeHash(entry);
```

Under concurrent requests, two or more middleware instances can read the same "last" entry before either writes, producing two entries that both reference the same predecessor — a fork in the chain. The integrity verifier (`VerifyIntegrityAsync`) iterates entries by timestamp order and compares `entry.PreviousHash` to `entries[i-1].Hash`, so forks will appear as invalid entries during verification.

This is not a correctness bug for low-traffic systems but becomes one under any meaningful concurrency. A queue or optimistic-concurrency retry on the hash write would fix it.

## Audit purge silently severs the chain

`PurgeExpiredAsync` deletes entries older than the retention cutoff:

```csharp
_logDb.AuditLogEntries.RemoveRange(expiredEntries);
```

After purge, the first remaining entry has a `PreviousHash` pointing to a now-deleted entry. The next integrity check will find that `entries[0].PreviousHash` does not match any existing entry. The check currently handles `i == 0` by skipping the previous-hash comparison only when `i > 0`, but if the first entry in the range has a non-null `PreviousHash`, it will still pass the recomputed-hash check — so integrity verification won't fail outright, but the chain is logically broken. A more serious issue: if someone deletes entries mid-chain (not just the oldest), the gap will surface as invalid entries.

## SignalR singleton lifecycle

The `signalr.ts` module creates a singleton `HubConnection` via module-level `let connectionInstance`. The `useSignalR` hook registers `onreconnecting` / `onreconnected` / `onclose` handlers every time any component mounts, without removing the previous handlers on unmount. SignalR's `.on*` callback registration accumulates — multiple performance page mounts will stack duplicate state-change handlers. The `on()` helper correctly calls `connection.off(eventName, handler)` on cleanup, but the lifecycle handlers (`onreconnecting`, `onreconnected`, `onclose`) have no corresponding removal.

## StorageReplicaController error masking

Every endpoint catches exceptions and returns `Ok(Array.Empty<...>())` or `StatusCode(500, ...)`, but the `GetPartnerships` endpoint returns `Ok` with an empty array on failure. The frontend has no way to distinguish "no partnerships exist" from "the server is unreachable" or "Get-SRPartnership failed." A 500 or a response envelope with an error flag would let the UI show an appropriate error state.
